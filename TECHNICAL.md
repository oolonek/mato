# Mato technical guide

[Read the plain-language overview](README.md).

## Run a job

Work from `mato/`. The checked-in `config/toy.toml` and `config/massive.toml` are portable examples. Copy the job you need to an ignored `.local.toml`, set its single `workspace` to an **existing writable directory** outside the source checkout, and leave the relative paths under `[dataset]`, `[database]`, `[picoto]`, `[indexes]`, `[annotation]` and `[knowledge_graph]` unless you need another layout. Both jobs can name the same workspace-root `mato/wikidata/*.sqlite` snapshots; their job databases and Picoto outputs remain separate. Keep `flock_root` relative to the config file and check the actual selected paths before resetting a job.

```sh
cd /path/to/oolonek/isla-gabriola-flock/mato
test -e config/toy.local.toml || cp config/toy.toml config/toy.local.toml
# Edit only workspace = "/path/to/your/writable/workspace" in config/toy.local.toml.
cargo run --release -- run --config config/toy.local.toml
```

`mato run` uses the job TOML to prepare optional inputs before loading the pipeline: configured public ZIPs and annotation references are downloaded and verified, while a prepared dataset with no `[dataset.archive]` uses its existing source files. With `[indexes].create_missing = true`, missing shared snapshots are built from QLever; complete ones are reused, and corrupted or incomplete nonempty snapshots are rejected. The toy job selects all stages through `kg_export` and `kg_validate`, finds the dataset ID by DOI and source root, creates a **new** N-Quads graph, validates it with Rust SHACL, and reports the graph path. A rerun reuses completed inputs and species state without erasing or resetting the job DB. Missing inputs/indexes require network access and Rust/Cargo. A prepared MassIVE job uses the same command with its own TOML and `--topN N`.

Inspect or deliberately refresh shared indexes without a second TOML:

```sh
./target/release/mato inspect --config config/toy.local.toml
./target/release/mato indexes refresh --config config/toy.local.toml --only taxon
./target/release/mato indexes refresh --config config/toy.local.toml --only chemical
```

`indexes refresh` is optional when `[indexes].create_missing = true`; it deliberately replaces a snapshot rather than merely filling a missing one. Do not refresh an index concurrently with another writer. `inspect` shows the resolved dataset, DOI, selected stages, DB, Picoto paths, index locations, and stored row counts when present; it reads SQLite without changing it. An independent job needs its own database and Picoto output outside its source dataset. Both toy and MassIVE templates select a full pipeline ending in graph export and SHACL validation; `--topN N` selects the configured top-N stages and isolated outputs instead of the full dataset.

**Interrupted shared-index refresh:** Stopping `indexes refresh` mid-transaction can leave a SQLite `*.sqlite-journal` alongside the index. The previous committed snapshot remains intact, but SQLite cannot roll back that journal through Cunaguaro's read-only connection (`Database has hot journal that must be rolled back`). Stop the refresh writer, **do not delete or move the journal**, then run the explicit Rust recovery command from `mato/`:

```sh
cargo run --release -- indexes recover --config config/massive.local.toml --only taxon
./target/release/mato run --config config/massive.local.toml --topN 300
```

`indexes recover` opens only the selected shared index read-write long enough for SQLite to roll back its journal, checks SQLite integrity and the committed snapshot generation/row count, and needs no QLever request. Use `--only chemical` for an interrupted chemical refresh; omit `--only` to check both. It never resets the job DB, deletes index files, or replaces the snapshot. If no complete snapshot exists, recovery refuses it: run `indexes refresh` when QLever is available. Re-running the full top-N job reuses its already-ingested rows; keep the same `--topN` value.

`annotation_runs` is a historical **attempt** count: a failed file retried twice has two rows. `annotation_current_runs` counts the latest attempt per registered file, so compare that with `spectrum_files` rather than expecting one annotation row per sample; files skipped before annotation have no attempt.

To start the **toy** job fresh, stop all Mato/species processes using its database or Picoto output. Restore `[pipeline].stages` in `config/toy.local.toml` to the full sequence needed to build the results (for example, `["validate", "ingest", "enrich", "picoto", "register", "annotate", "chemical_enrich", "kg_export", "kg_validate"]`), then inspect the config again. Only when deliberately discarding a previous job, delete that configured database, SQLite sidecars, and Picoto output directory **permanently** with explicit confirmation (for MassIVE top-N, use the separate procedure below instead):

```sh
./target/release/mato reset --config config/toy.local.toml --yes
./target/release/mato run --config config/toy.local.toml
```

`reset` refuses paths inside the input dataset or source tree and an output directory that contains either. **It cannot know whether other jobs share the configured database or output directory.** Do not reset `config/massive.local.toml` without `--topN` or another shared job. `reset --config config/massive.local.toml --topN 250 --yes` is only for deliberately deleting that isolated N's DB and Picoto output; it does not delete production outputs or the old top-N database. Running a resume-only stage list such as `["annotate"]` against a freshly reset database cannot work; include `ingest` and required earlier stages.

To **resume**, do not reset. Keep the database and Picoto files, edit the selected stage list to begin at the stage needing retry, and keep later dependent stages in order. For example, after successful registration and partial annotation in a MassIVE top-N run, use `top_n_stages = ["annotate", "chemical_enrich", "kg_export", "kg_validate"]` with the **same `--topN 250`** on each command: unchanged successes and completed chemical lookups are reused, while failed annotation files are retried. After regenerating Picoto files, rerun `register`. There is no automatic checkpoint. For a full-stage rerun without deleting data, restore the full `top_n_stages` list in the same TOML and keep `--topN 250`.

Inspect any existing table or view without typing a database path:

```sh
./target/release/mato show annotation_current_runs --config config/toy.local.toml --limit 20
./target/release/mato show annotation_runs --config config/toy.local.toml --limit 200
```

`show` uses Peregrino's read-only table preview. If the DB is missing, it reports that explicitly rather than returning SQLite's “unable to open database” error; run the configured pipeline with `ingest` selected before inspecting results. Add `--verbose` to `run` for dispatched filenames and Cunaguaro per-name output.

## Run reports

Each `mato run` with a valid job config writes a new Markdown report in `reports/` beside the selected SQLite file (for `--topN 250`, `<top_n_root>/250/reports/run-<timestamp>-<pid>-<sequence>.md`). Mato prints the exact report path at the end, even for a partial or failed pipeline. Reports are atomic, are never overwritten, and survive `mato reset` so you can compare attempts. If the report itself cannot be written, Mato exits nonzero; an earlier pipeline error remains the primary error. A force-killed process cannot finalize a report.

The report records `complete`, `partial` (per-file annotation errors; later stages used saved hits), or `failed` (fatal stage error); selected stages and row limit (`250` for `--topN 250`, no limit when omitted); dataset DOI, input and selected output locations, a link to the emitted graph when one exists, and whether SHACL validation completed; dataset-specific counts of ingested samples, spectra, registrations, current annotation hit files and hits; and a database-wide chemical lookup count. A partially annotated graph can be SHACL validated while the report remains `partial` and Mato exits nonzero: shape conformity does not establish annotation completeness. The row limit describes **up to N metadata rows after optional filtering and sorting**, plus their referenced raw files—not how many records this invocation added. Counts are **database state at finish**, not counts of new records in this invocation. An unavailable DB or table is shown as **not available**, not zero. The failed-file section lists the latest outstanding annotation error per file for this dataset, including taxon/QID/reason and whether the error was recorded during this run; new errors from other datasets in a shared DB are included with their dataset ID. A report can still be generated if the DB cannot be read, with the inspection failure shown instead of invented metrics. Copy the report's `inspect` and `show` commands to inspect the live DB, or its `kg query` command to run a coverage query over an exported graph; the saved report is a snapshot, while the database may change on retries or reset.
`Outstanding failed files` counts only this dataset's latest unresolved annotation errors; the table may additionally show errors newly recorded for other datasets in a shared database.

## Example: download the Zenodo toy dataset and export a KG

**One editable path, one command.** From `mato/`, copy [config/toy.toml](config/toy.toml) once, set `workspace` in your ignored copy to an **existing writable directory** outside the checkout, and run:

```sh
test -e config/toy.local.toml || cp config/toy.toml config/toy.local.toml
# Edit workspace = "/path/to/your/writable/workspace" in config/toy.local.toml.
cargo run --release -- run --config config/toy.local.toml
```

In plain language, Mato checks/downloads the toy spectra and annotation references, checks/creates reusable Wikidata lookup tables, processes three metadata rows and six spectra, writes a Markdown run report and a **new** graph file, and validates that graph. The command prints the graph path and a ready-to-run SPARQL query command. It does not require `unzip`, `curl`, `sqlite3`, Python, or Just. Allow disk space and time for the reference MGF (~939 MB), LOTUS CSV, and multi-million-row Wikidata snapshots on a clean machine.

The toy TOML's optional `[dataset.archive] doi` names the [version-specific Zenodo record 10018590](https://zenodo.org/records/10018590) for the toy concept DOI [10.5281/zenodo.10018264](https://doi.org/10.5281/zenodo.10018264); it is distinct from `[dataset].doi`, which identifies the ingested dataset. On first preparation Sapayoa verifies the ZIP receipt and Mato checks extracted ZIP entries; subsequent runs reuse the prepared tree when the receipt, metadata and raw directory exist, rather than rereading every raw file. Do not manually modify a prepared source tree: this fast path does **not** rehash extracted raw spectra. The configured reference MD5 checks still run before every annotation. Existing complete shared indexes are reused; a mismatched reference or incomplete nonempty snapshot stops the run instead of silently replacing it. All output paths resolve from one workspace, outside the downloaded source and checkout. `kg_export` creates a uniquely named N-Quads file under `[knowledge_graph].output_dir`, and `kg_validate` checks SHACL shapes. A rerun never resets DB/Picoto results or overwrites an earlier graph.

To inspect the job or run a bounded example query, use the paths printed by `mato run`:

```sh
./target/release/mato inspect --config config/toy.local.toml
./target/release/mato show annotation_current_runs --config config/toy.local.toml --limit 20
./target/release/mato show chemical_lookups --config config/toy.local.toml --limit 20
# Paste the printed Peregrino kg query command; it includes the exact graph path.
```

The graph links local sample records, analyses, features and ranked **candidate** annotations to Wikidata taxon and chemical QIDs; a candidate does not prove a molecule is present. [Peregrino's KG semantics](https://github.com/oolonek/peregrino/blob/master/TECHNICAL.md#wikidata-linked-local-knowledge-graph) explain the joins. For graphs too large for in-memory SHACL/query, see [QLever indexing](https://github.com/oolonek/peregrino/blob/master/kg/QLEVER.md). The same configured `mato run` processes prepared datasets and optionally manages inputs where sources are specified.

[Just](https://just.systems/man/en/) is an optional command runner, not a downloader or integrity check. A `just toy` wrapper around this one command would add an installation and another file without removing any remaining setup, so no Justfile is required.

## Example: first 25 MassIVE records with reported organs and collectors

The [MassIVE job template](config/massive.toml) selects the complete source-to-graph workflow without `--topN`; that processes the **entire** prepared dataset and can take substantial disk, time and validation memory. Copy it to ignored `config/massive.local.toml` and set the **same workspace** used in the toy job to reuse the shared `[indexes]` snapshots and reference files. Without `[dataset.archive]`, Mato does not download the MassIVE source dataset. With `--topN 25`, the template's `[selection]` requires nonblank `observation_subject` and `collector_full_name`, sorts matching metadata rows by `filename`, and takes **up to 25 matching rows** before `validate` and `ingest`. The actual organ header is `observation_subject`, not `organ_processed`. `top_n_stages` runs in an isolated database at `<top_n_root>/25/flock.sqlite`, Picoto output at `<top_n_root>/25/picoto`, and graph directory `[knowledge_graph].output_dir/25`. From `mato/`, run:

```sh
cargo run --release -- run --config config/massive.local.toml --topN 25
./target/release/mato inspect --config config/massive.local.toml --topN 25
./target/release/mato show annotation_current_runs --config config/massive.local.toml --topN 25 --limit 200
```

`[selection].require_nonempty` combines **all** named source-column checks (logical AND), so a blank or whitespace-only organ **or** collector excludes the row. Each `[[selection.sort]]` names an existing metadata header and an optional `descending` boolean; keys are compared lexicographically and ties keep original source order. Sorting precedes `--topN`; omitted `[selection]` preserves the old first-N-in-source-order behavior. Filtering counts metadata rows, **not raw spectra**: a row referencing multiple MS files can produce more than 25 spectra. Positive-only annotation can skip negative-mode files, and a SHACL-conforming graph can still be partial if some annotations fail. The source TSV is untouched. Mato writes a small, immutable, content-addressed selected TSV under `<dataset_root>/.mato-selections/`, inside the original dataset root because Machaca and Peregrino enforce that metadata paths stay there; it hashes the source bytes, filter/sort rules and N. The snapshot path is stored in SQLite and the Markdown run report. To run the filtered job, the dataset directory must be writable; the raw files and original TSV are **never rewritten**. The selection is ignored when `--topN` is omitted. If none match, the run fails before ingest.

On an existing top-N database, Mato rejects a changed selection/source snapshot rather than silently mixing different files. To start fresh with **the same N** after changing filters, stop its processes and use `mato reset --config config/massive.local.toml --topN 25 --kg --yes` (only if you also intend to remove its graphs and QLever backends); otherwise omit `--kg`. Other N jobs, shared Wikidata indexes and downloaded MassIVE data remain. A resume with unchanged selection/N can shorten `top_n_stages` to `["kg_export", "kg_validate"]` and reuses the selected TSV and DB without rerunning annotation. With `[knowledge_graph].allow_partial = true`, logged per-file annotation errors do not prevent graph export/SHACL validation, but the job reports `partial` and exits nonzero. Reset does not purge `.mato-selections/` because snapshots are content-addressed and may be shared by other jobs; they are small and never source data.

**To make the new Leaf QLever example return links rather than merely selecting reported organs:** Mato does not implicitly approve a source word as a Wikidata item. In `config/massive.local.toml`, temporarily set `top_n_stages = ["validate", "ingest"]` and run the same `--topN 25` command above. Check the selected DB's values (`sqlite3 /media/nvme8tb/isla-gabriola/mato/top-n/25/flock.sqlite "SELECT observation_subject, count(*) FROM sample_rows GROUP BY 1"`); the reviewed `Leaf` mapping can be imported only if `Leaf` is actually present. Follow [Peregrino's reviewed mapping import](../peregrino/kg/OBSERVATION-SUBJECT.md#add-or-change-a-mapping-one-repeatable-procedure) **against this selected DB**, not a full-MassIVE DB. Then set `top_n_stages = ["enrich", "picoto", "register", "annotate", "chemical_enrich", "kg_export", "kg_validate"]` and run `--topN 25` again. The exported graph now includes imported links. Register **that new graph** in QLever with a new name/port; the UI Leaf example is already available. If `Leaf` was not selected, change the ordering or N and use a fresh isolated top-N job; never claim unmapped values are QIDs.

## Serve exported graphs with QLever

**In plain language:** Each exported `*.nq` graph can become its own SPARQL endpoint. The endpoints appear as separate choices in **one** QLever UI; the UI does not merge their data. Run `mato qlever add` once per graph on the server, then use `mato qlever access` to print the SSH tunnel for a laptop. A graph with failed annotation files stays partial after indexing; a successful QLever query does not make those files complete.

**Prerequisites:** Docker must run on the server; the [official QLever UI installation guide](https://github.com/qlever-dev/qlever-ui/blob/master/docs/install_qleverui.md) explains how to build a compatible `qleverui:latest` image locally. Mato uses a fixed QLever engine image digest for **both** indexing and serving, not a moving `latest` tag. The UI image is a separate Django application; the Mato helper is Rust, but starts Django's management commands *inside that image*. No host Python, QLever CLI, Just, or second pipeline config is required. The templates' shared `[qlever]` settings choose `mato/qlever-indexes`, `mato/qlever-ui`, UI image `qleverui:latest` and server-loopback UI port 7044 relative to the same `workspace`. Set `ui_image` once in both job TOMLs if your locally built UI image has another tag. Docker may need to pull the pinned engine digest the first time.

Take each graph's exact N-Quads path from the printed `mato run` output or Markdown report; do **not** pass a SQLite DB or its containing directory. On the server, from `mato/`, replace the two example `--graph` arguments with your actual files:

```sh
./target/release/mato qlever add --config config/toy.local.toml \
  --graph /path/to/toy-graph.nq --name toy --port 7043
./target/release/mato qlever add --config config/massive.local.toml \
  --graph /path/to/massive-50-graph-partial.nq --name massive-50 --port 7045
./target/release/mato qlever access --config config/toy.local.toml \
  --ssh allardpm@allardpm-commons
```

The first command mounts the existing N-Quads file **read-only** into the QLever indexer, builds a new index under `<workspace>/mato/qlever-indexes/toy` without copying the graph, and publishes port 7043 on `127.0.0.1` only. The second creates a *different* index and localhost API on 7045. Both register their own backend and four Mato-managed example SPARQL queries in the shared UI database under `<workspace>/mato/qlever-ui`. An existing backend with the same name, graph path, size, modification time and port is reused, never overwritten; running the same `qlever add` again also syncs the example queries from source. A stopped matching engine or UI is restarted. Choose a new name for a new export. A completed build can be resumed if its source receipt matches; an incomplete or unrecognized index directory is refused, not reindexed in place. The helper does not rehash a graph on reuse: **do not edit an indexed graph in place**, especially while preserving its size and timestamp. Do not delete the shared UI SQLite database while backends are registered. Set `[qlever].index_root` and `.ui_data` to the **same workspace paths** in all job configs sharing one UI. Use distinct names and unused engine ports, different from `[qlever].ui_port`. `mato reset` leaves KG and QLever artifacts in place unless `--kg` is specified.

The access command **prints** one `ssh -N -o ExitOnForwardFailure=yes ...` command; copy and run it on the laptop, leaving its terminal open. It forwards laptop `127.0.0.1:17044` to the server's UI port 7044 and forwards **each** registered engine port to the **same** laptop port. Open `http://127.0.0.1:17044/toy` or `/massive-50` in the laptop browser. The UI's JavaScript calls `http://127.0.0.1:7043/` or `:7045/` directly; forwarding only the UI port gives a broken query surface. Check `http://127.0.0.1:7043/ping` and `:7045/ping` on the laptop after tunneling. A bare QLever API URL without a SPARQL query may say “Unknown path”; `/ping` is the readiness check. If a laptop API port is occupied, choose another engine port when first registering the graph; `--local-ui-port` changes only the UI tunnel. Use a hostname **reachable from the laptop**, not necessarily the server's local machine name.

For a direct server-side SPARQL check, POST one of [Peregrino's example queries](../peregrino/kg/coverage.rq) to the appropriate localhost port:

```sh
curl --fail-with-body --silent --show-error \
  --header 'Accept: text/tab-separated-values' \
  --data-urlencode 'query@../peregrino/kg/coverage.rq' \
  http://127.0.0.1:7043/
```

**Where the UI examples live:** `mato/src/qlever.rs::register_ui` lists their names; the actual SPARQL files live in `peregrino/kg/` (`coverage.rq`, `toy-candidates.rq`, `taxonomic-evidence.rq`, `leaf-observations.rq`). They are copied into the shared UI SQLite database at registration, not read on each page load. The older `peregrino/kg/qlever-ui.yml` belongs to the manual legacy deployment; Mato's helper does **not** read it. The **Reviewed Leaf observation subjects** example returns source text, the approved [leaf QID](https://www.wikidata.org/wiki/Q33971), file names and independent taxon/collector links. It does not require any chemical annotation. After editing a managed query file, rerun the **same** `mato qlever add --config ... --graph ... --name ... --port ...` for each existing backend whose example should be updated; no reindex occurs. Empty Leaf results on toy or a subset without reported leaves are expected. An example update does not add missing triples to an old graph: [import the reviewed mapping](../peregrino/kg/OBSERVATION-SUBJECT.md), export a **new** graph and register it under a **new** backend name/port.


**Security and resource boundaries:** Engine ports are Docker-published to loopback only; the Linux host-network UI binds Gunicorn to loopback. This does **not** provide authentication, TLS or authorization. Do not publish these services on `0.0.0.0` or expose private metadata without a rights review. Docker [warns](https://docs.docker.com/engine/network/port-publishing/) that releases before 28.0.0 could leak even loopback-published ports to the same L2 network; upgrade or add network isolation before serving private graphs. The UI is created from an empty migrated SQLite database rather than copying a demo admin account; anyone who can reach its localhost port can run queries. Default QLever query memory is 2 GiB; large graphs can require more index disk/memory than the toy. Index files and UI state persist independently of the source graph and Mato DB; stop containers deliberately by their `mato-qlever-NAME`/`mato-qlever-ui` names, and never overwrite a live index.

## Config contract

`[pipeline].stages` is an ordered, nonempty subset of `validate`, `ingest`, `enrich`, `picoto`, `register`, `annotate`, `chemical_enrich`, `kg_export`, `kg_validate`; both toy and MassIVE templates select the full sequence for an ordinary run. `kg_export` writes a fresh graph; `kg_validate` requires `kg_export` earlier in the selected list. For `--topN N`, `[pipeline].top_n_stages` takes the place of `stages`, `[database].top_n_root` supplies isolated DB/Picoto paths, and `[knowledge_graph].output_dir/N` supplies an isolated graph directory. A positive N and `top_n_stages` are required. Edit the appropriate list to resume without repeating processing; taxon `enrich` reuses matching results from the current shared index generation. Maintain dependency order. To check only metadata, use `["validate"]`. Selected commands still require their inputs to exist: `register` requires matching `_ms2.mgf`, `_features.tsv` (feature audit, not `_feature_list.tsv`) and `_sirius.mgf` for every selected mzML/mzXML. Without `--topN`, every supported raw file under the configured raw tree is eligible; with `--topN N`, Mato filters by `[selection].require_nonempty` if configured, sorts by its `[[selection.sort]]` keys, then selects up to N metadata rows and their referenced raw files. Without `[selection]`, top-N preserves source order. Mato checks for all three outputs before writing any registration.

`enrich` uses `[indexes].taxon_index` and `chemical_enrich` uses `[indexes].chemical_index` from the **same job TOML**. Set both to persistent paths in a common workspace to share complete snapshots across jobs. `[indexes].create_missing = true` builds missing snapshots during `mato run` but does not replace incomplete nonempty or stale ones. `mato inspect --config CONFIG` reports their paths and presence. Refresh both deliberately with `./target/release/mato indexes refresh --config config/toy.local.toml`, or use `--only taxon` or `--only chemical`. `mato reset` leaves both shared indexes untouched.

`chemical_enrich` is optional and runs `cunaguaro chemical-enrich --db <database>` after `annotate`. It reads current annotation hits by **full** library InChIKey, reuses previous lookup results and stores possibly multiple Wikidata chemical items per key; a candidate match does not establish chemical presence in the sample. It needs hocofaisan's annotation tables in the existing database but does not need the annotation files on disk when selected alone: use `stages = ["chemical_enrich"]` for an ordinary run or `top_n_stages = ["chemical_enrich"]` with the same `--topN N` to resume after top-N annotation, including after an annotation run with recorded per-file errors. Use the Cunaguaro CLI directly for non-default batch size, lookup limit or refresh. `cunaguaro propose --db <database>` prints the graph proposal and logs identities needing review.

To avoid per-key WDQS requests in `chemical_enrich`, keep the shared chemical snapshot at `[indexes].chemical_index` in your job config. `[indexes].create_missing = true` builds it during `mato run` if absent; with the setting false, prepare it explicitly via `./target/release/mato indexes refresh --config config/massive.local.toml --only chemical`. Mato passes the shared file read-only to Cunaguaro and reports whether it is present in `inspect`; a missing configured index fails before starting stages when not built. `mato reset` deletes only the selected job's DB/Picoto outputs, not the shared index. Refresh explicitly when needed (for example weekly), not concurrently with writers. See [Cunaguaro](https://github.com/oolonek/cunaguaro/blob/master/TECHNICAL.md#bulk-qlever-chemical-index) for the advanced standalone CLI and offline `--from-db` option.

`workspace` in the job TOML is an absolute writable root for dataset folders, job DBs, Picoto outputs, annotation references, shared indexes and graph exports; relative paths resolve beneath it, not the process directory. Absolute paths remain absolute. `flock_root` and `[annotation].settings` resolve relative to the job TOML file; `dataset.metadata` and `dataset.ms_dir` resolve inside the dataset root. `[dataset.archive] doi` optionally enables version-specific Zenodo single-ZIP preparation; omit it for an already prepared dataset. `[annotation.library_source]` and `[annotation.lotus_source]` optionally specify `url` and `md5` for verified references; LOTUS additionally takes `compression = "gzip"` to expand the downloaded CSV. Without sources, these files must already exist. `[knowledge_graph].output_dir` selects fresh graph exports; `.allow_partial = true` explicitly permits export/validation despite per-file annotation failures (the toy uses false and refuses partial export). With `--topN N`, the DB and Picoto paths derive from `top_n_root/N/`, and graph files from the graph output directory's `N/` child. The dataset DOI is supplied by the operator. Paths outside the dataset root for metadata or raw spectra are rejected. The required annotation files are checked before any stage runs if `annotate` is selected.

`[dataset].taxon_column` is required even when `ingest` is not selected. Set it to the **exact metadata TSV header** containing the taxon names (for example, `source_taxon` in the toy dataset or `taxon_scientific_name` in MassIVE). Mato rejects an absent or blank selection before running stages, then passes this **same TOML file** to `peregrino ingest --config`; Peregrino rejects a header not present in the metadata before changing the database. There is no automatic taxon-column selection or separate Peregrino mapping. Keep the pipeline TOML outside the source dataset unless you deliberately choose a path there.

Mato uses `cargo build --release` for the selected species, then invokes their release binaries. Cargo must be available; `CARGO` and `CARGO_TARGET_DIR` are honored if set. Reusing a config reuses Cargo's build cache. Stages remain ordered because later stages depend on earlier results; independent work *within* a stage can run concurrently. Each stage announces its species with an emoji, name and brief description. During registration the progress bar shows the latest completed raw filename; `--verbose` prints dispatched paths and forwards to cunaguaro for per-name results. Picoto prints its own per-file results. The underlying programs still print progress and summaries. Peregrino and Picoto both use 🦈 because both are sharks.

In `config/massive.toml`, `[peregrino] jobs = 4` bounds concurrent per-file registrations (ingestion remains one SQLite transaction), and `[picoto] jobs = 25` bounds Picoto file workers. Taxon enrichment reads the shared local index rather than pacing per-name Wikidata requests. Mato launches Hocofaisan as a child process, which annotates one file at a time; spectral-matcher parallelizes scoring **within each file** using its native Rayon pool. Set `RAYON_NUM_THREADS` on the Mato command to cap the workers inherited by Hocofaisan (for example, `RAYON_NUM_THREADS=16`); 30 or the machine maximum is not guaranteed faster. Compare elapsed time or files per minute for representative files before choosing a value; do not start competing annotation processes against the same SQLite database to simulate file-level concurrency. Missing optional `[peregrino]` defaults to one worker.

During registration, concurrent peregrino processes validate and hash separate files, but their short SQLite write transactions serialize using an immediate write reservation. If registration is interrupted, `["register", "annotate"]` repeats registration without regenerating Picoto outputs; leave `picoto` in the list only if outputs need regeneration. A competing long-running database writer can still exhaust SQLite's 30-second wait.

Re-running stages delegates idempotency to the species: peregrino re-ingests a dataset transactionally, cunaguaro reuses stored successful QIDs and retries missing/failed taxon resolutions (run cunaguaro directly with `--refresh` to recheck successes), Picoto rewrites selected outputs, registration validates and replaces per-raw references, hocofaisan reuses unchanged successful annotation runs, and cunaguaro chemical enrichment reuses completed lookups. There is **no pipeline checkpoint or automatic retry**. If a stage fails, inspect its error and edit the selected stage list (`top_n_stages` with `--topN`, otherwise `stages`) only after confirming the required earlier state; in particular, do not skip registration after regenerating MS2 files.

Do not start a second enrichment against the same SQLite database while a pipeline is running. An already-running cunaguaro process cannot pick up a newly built binary or changed TOML settings. Let the current run finish unless you intentionally want to stop it; restarting `enrich` skips saved successful QIDs, retries saved errors and processes taxa without a saved result. Enrichment remains database-wide, including taxa from other datasets in the same SQLite file.

Hocofaisan uses a positive-mode library only. It skips MassIVE rows with `ionization_mode = "negative"`, but unresolved taxa, absent LOTUS taxa, missing registrations, empty/invalid query MGF or other per-file annotation errors are recorded in SQLite. After completing eligible files, Hocofaisan exits `2` when any per-file errors were recorded (`1` remains a fatal stage failure). Mato treats only this `annotate` exit `2` as partial: later configured stages run on saved current hits, including `chemical_enrich` and, if `[knowledge_graph].allow_partial = true`, `kg_export` and `kg_validate`. Mato then exits nonzero with a reprocessing warning rather than claiming full success, even if SHACL validation succeeds. The error rows remain in `annotation_runs`; successful unchanged files are reused and failed files are retried on the next `annotate` run. Other stage failures still stop immediately. Hocofaisan currently processes all eligible ingested rows in the DB, not only the dataset configured in Mato.

Run `cargo test --manifest-path mato/Cargo.toml` for config and CLI regressions. Managed ZIP extraction and configured reference MD5 checks run during `mato run`; metadata validation alone does not prove downloaded-byte integrity.
